## 第一项 Docker 故障分流

**现场证据。** `CVE-2026-119705`、`CVE-2026-19040`、`CVE-2026-2207` 的日志包含 Docker named pipe 不存在；`CVE-2026-22200` 包含构建状态流的 gRPC Unavailable／EOF。这些错误原先被归为可由作者修复的 build_error，并消耗了作者续写次数。另有部分超时日志只有命令行和 TIMEOUT，没有构建输出。

**修改。** 构建前用有 10 秒上限的引擎探针检查可用性；明确的引擎连接错误归为可重试的 infra_error。构建中途超时后再次检查引擎：引擎失联时不要求作者改代码，正常引擎上的构建超时仍保留 build_error。准备共享基础镜像时也保留 infra_error 分类，不再统一包装成题目构建错误。

**重测。** 使用独立、不可用的测试 Docker endpoint，真实调用构建入口，结果为 infra_error 且 auto_repairable=false；随后恢复正常连接，共享 verifier/environment 镜像可直接复用。复用 `CVE-2026-3788/task/tests` 的原构建上下文，verifier 在 13.62 秒内构建成功，测试标签随后删除。

这里验证的是错误分流、提前失败和健康环境下的阶段恢复。13.62 秒也受当前缓存与引擎状态影响，不能解释为分类修改使所有历史超时都变快；没有将 14 个超时一概认定为同一原因，也没有把它们改记为已通过。

## 第二项 空补丁的来源恢复

**现场证据。** `CVE-2026-10130` 的 `src-5-upstream-commit` 是零字节，状态却为 ok。作者指出只读证据无法满足最短引用要求并放弃。原实现从 URL 取得提交 SHA 后，接受了这份空正文。

**第一轮修改与重测。** 空正文不再作为修复证据，继续走已有 API 回退。真实重测发现，网页 `.patch` 和 API 的 patch media 响应都是空正文，单纯回退仍不能恢复。

**第二轮修改与重测。** 同一个 API 请求 JSON media 可以取得 4,726 字节的提交信息与文件补丁，因此将 commit API 的 Accept 改为 JSON。再次执行原提交的来源采集，成功得到 `e6a49f508191d0f1bdad0f146da43819e7849f18` 的非空证据。两个来源都为空时不会生成有效的 fix source。

采集的新文件位于 `work/iteration-20261116/CVE-2026-10130-json-replay/`。本轮没有重新出题或将原 UNSUPPORTED 状态改为发布；证明的是导致放弃的证据采集问题已修复。

## 第三项 XSS bot 的真实运行依赖

**现场证据。** `CVE-2026-15920` 两个变体的 author probe 都记录 `ModuleNotFoundError: No module named 'playwright'`。使用当时的官方基础镜像再次导入 `playwright.sync_api`，确认同样失败。

**重测。** 在无外网的真实容器中运行框架现有 bot，访问本地测试页面，浏览器执行页面脚本并回传其会话 cookie，`/visit` 返回 200。还运行了 Compose／判题器的容器回归，确认修复版隔离回放和固定负例仍按预期工作。

## 第四项 无效 solver 运行不送题目审查

**现场证据。** `CVE-2026-119653` 的已保存 solver trial 包含 `exception_type=AgentAuthenticationError`，却仍进入 reviewer，最终作为题目 validation_error 触发修订。通用 failure_type 还将它显示成 agent_exception。

**修改。** 进入 reviewer 前先检查真实 solver trial：有执行异常或没有 reward 的运行归为 infra_error，保留异常类型和 trial 位置，不把它当成题面或解法缺陷。新运行先保存 `solver-result.json`，即使没有进入审查也留下阶段结果；读取审核缓存时同样检查其 solver 观测。正常执行得到 reward=0 的试解仍可进入审查。

**重测。** 直接加载原 `solver-review.json` 中的 solver 结果，执行修改后的审查入口，准确得到 AgentAuthenticationError 对应的 infra_error。该回放的 reviewer 调用、author 调用均为 0。后续检查 `CVE-2026-27498` 时又观察到 UnknownApiError，修改后的入口同样在模型审查前停止。benchmark 报告也保留 Harbor 的 `exception_type`，不再将它们统称为 agent_exception。

## 第五项 reviewer 的可用证据被输入截断

**现场证据。** 为核实“缺少补丁”的反馈，重建了两个已完成审查的实际输入。`CVE-2026-21894` 的运行时元数据有 425,779 字符，`CVE-2026-27498` 有 420,872 字符，主要来自完整 npm 依赖清单。这些内容排在原始证据之前，而 reviewer 只接收前 90,000 字符，导致两个样本已有的修复补丁均未送达模型。原补丁文件分别有 18,000 和 6,880 字节。

**修改。** 保留规格、目标镜像身份、主产品版本和依赖数量，将完整传递依赖列表换成这些相关字段；把规格引用的修复来源放在证据段首位。没有增加 reviewer 或放松审核条件。新的证据上下文分别为 64,656 和 63,209 字符，引用的修复补丁均处于实际发送窗口内。

**重测。** 复用 `CVE-2026-21894` 的原任务文件和有效 solver 结果，只调用一次已有 reviewer。其机制判断由 uncertain 变为 supported，并引用了实际修复提交 a61a599 中的签名校验变更。审查仍返回 revise：它指出题面宣称 workflow.json 同时包含两个路由参数，而文件实际只包含 webhookId。该文件与题面矛盾已手工核实，保留为后续题面修订的具体反馈，未将此题改为发布。

`CVE-2026-27498` 的原 solver 结果包含 UnknownApiError，因此这份 checkpoint 不足以支持新的题目审查；按第四项修复在调用模型前归为基础设施错误，不用一份无效试解强行换取审核结论。

七类修复的阶段回放共执行 1 次 reviewer 模型调用，CLI 报告费用为 0.797525 美元，记录在独立回放文件中；作者和 solver 没有重跑。审核反馈改变说明原输入截断会影响判断，不构成独立专家对 CVE 正确性的认证。随后针对 `CVE-2026-21894` 题面修订的独立试验又执行了 1 次 solver 和 1 次 reviewer，见本文末尾。
